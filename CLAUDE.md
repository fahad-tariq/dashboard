<ARCHITECTURE>
Go + chi + htmx server-rendered dashboard for one owner. Markdown files are the source of truth for tasks, goals, ideas and house; SQLite holds users, sessions and commentary only. The `tracker_items` table is unused (the mirror was dropped; `Summary()` counts from the in-memory cache), but `auth.DeleteUser` still deletes from it, so update that before dropping the table.

Plan history, decisions and measurements live in the "Working notes" of `docs/plans/01-foundations-and-modules.md`, one `### Phase N notes` section per phase (Phase 6 module framework, 7 module migration, 8 live refresh and morph, 9 styles). Small follow-ups are in `docs/backlog.md`.

**Modules** (`internal/module`, adapters in `internal/modules/`): every feature area is a module registered with one line in `app.modules` (`internal/app/app.go`). Built-in: `todos` (personal tracker and goals), `family`, `house`, `ideas`. A module implements `Manifest()` and `Routes(r)`, plus optional capabilities: `APIRouter` (mounted under `/api/v1/<module-id>`), `Watcher` (exact-filename `WatchSpec`s), `Searcher`, `HomeWidget` (returns `[]WidgetData`, data not HTML). It receives one `module.Deps` (location, config, service registry, renderer, `DataDir`, commentary store, `Publish`). `module.NewRegistry` fails start-up on duplicate IDs, overlapping or reserved prefixes, reserved shortcut keys (`h c d / ? n k`), nav paths outside the module's prefixes, or more than 6 primary nav links. Browser routes are registered on a scratch router; any route outside `Manifest.Prefixes` fails start-up, the rest are copied onto the real router. Templates live in `web/templates/<Manifest.Templates or ID>/`. `internal/module/moduletest` is a permanent fixture module (never registered in production) exercised by `TestModuleContract`; copy its shape when adding a module. It renders through `Deps.Render.Page`, which merges `auth.TemplateData` and resolves `?msg=` from `Manifest.Flash`. The four built-in modules do not: they wrap the existing feature handlers (`tracker.Handler`, `ideas.Handler`, `house.Handler`), which take `deps.Render.Lookup(dir)` and resolve flashes with each package's own `resolveFlash` and `flashErrorKeys`.

**Adding a module beyond the fixture's shape:**
- Storage: `services.Registry` (`internal/services/registry.go`) hard-codes the personal, ideas, family and house services, their per-user paths (`pathsFor`) and their `OnChange` → publish wiring (`SetPublisher`). A new module should own its service and call `Deps.Publish(id)` after writes rather than extend the registry. Shared files go in `Deps.DataDir`; per-user files use `WatchSpec.UserFile`.
- Soft delete: the hourly purge (`appServices.purgeExpired` in `internal/app/app.go`) names every service; a new module's trash is never purged unless it is added there.
- Select mode: `tracker.js` `toggleSelectMode` only looks for `.tracker-page, .ideas-page`.
- New routes change the route goldens: regenerate with `go test ./test -run TestRouteGolden -update` and explain the diff in the plan.

Adapters live in `internal/modules/`, not in the feature packages, because `module` imports `services`, which imports `tracker`/`ideas`/`house`: a feature package importing `module` is an import cycle. The feature packages (`tracker`, `ideas`, `house`) keep their parsers, services and handlers.

**Core pages are not modules:** home and planner, calendar, digest, search, auth, account, admin, uploads, commentary. Home reads tracker services directly through `home.Lists`; a `Plannable` capability is deferred to Plan 2.

**One wiring path:** `app.NewRouter` builds everything; tests use `app.NewRouterWith(..., app.Options{Modules, Broker})`. `internal/app` is split into `app.go` (users, services, watcher, sessions, purge loop), `routes.go` (mounting, middleware), `templates.go` (func map, parsing, start-up contrast check), `fragment.go` (htmx fragment middleware) and `static.go`. `cmd/dashboard` loads config, opens the DB, calls it and runs the `useradd` and `migrate-data` subcommands.

**Auth modes:** auth is on by default. `DASHBOARD_AUTH=disabled` swaps `RequireAuth` for `auth.InjectUser(db, 1)`, so every request is user 1; the server refuses that mode unless `ADDR` is loopback. With auth on and no login-capable users, `DASHBOARD_PASSWORD_HASH` creates an `admin@localhost` admin; without the hash it refuses to start. No-auth creates a `local@localhost` placeholder as user 1 that cannot log in (`auth.LoginUserCount` ignores it). If that database later starts in auth mode, the bootstrapped admin gets a later id while the API and user-1 paths still point at the placeholder; dev databases only. No-auth reads user 1's files from `PERSONAL_PATH`/`IDEAS_PATH` via `Registry.SetUserPaths`; auth mode uses `USER_DATA_DIR/1/`. Both modes register identical routes. Admin and multi-user code is frozen: no new work, no deletion.

**API:** `/api/v1` is mounted only when `DASHBOARD_API_TOKEN` is at least 32 characters; the bearer token acts as user 1 and goes through the same resolvers as the web handlers. It sits outside cross-origin protection. Production runs with the API and MCP sidecar disabled.

**Writes and change events:** every markdown write goes through `internal/atomicfile.Write` (temp file, fsync, rename, fsync dir); never `os.WriteFile` a data file. Services follow read-modify-write under a mutex (`mutate(slug, fn)` / `mutateBatch(slugs, fn)`; a batch with any missing slug writes nothing). Each service embeds `changes.Recorder`: after a write it records the content hash and publishes `changed:<module-id>` through the broker's debounced publisher (500ms). The watcher calls `ResyncIfChanged`, which skips re-parsing and broadcasting when the file matches the service's last write. So one mutation from web, API or MCP gives exactly one event and zero re-parses; an external edit gives one of each. `services.Registry.SetPublisher` maps personal to `todos` and both house files to `house`.

**Live refresh and morph swaps** (`web/static/live.js`): `<body hx-ext="sse,morph" sse-connect="/events">` is never swapped. Live pages (home, todos, family, goals, ideas, house) have one `[data-live]` container carrying `hx-select`, `hx-target` and `hx-swap="morph"`; its `live-refresh` child (`_components`) holds the `hx-get` and the `sse:changed:<id>` trigger, and its attributes never change (htmx re-initialising an element whose attributes change would stack EventSource listeners). Calendar, digest, account, admin and idea detail have no live container. Expanded state lives in three places: tracker and idea rows toggle `minimised` (`tracker.js`), house detail rows toggle `house-detail-hidden` on a sibling `<tr>` (`house.js`), plan rows use `planItemClick` (`planner.js`). Client-owned state survives morphs by declaring it in markup: `data-keep-class`, `data-keep-attr`, `data-morph-skip` (upload area, commentary slot), `data-client-*`. A refresh that must wait (mid-drag, confirm dialog open, form in flight) goes through `liveRefresh.hold/release` and is queued, never dropped.

**Fragment responses** (`internal/app/fragment.go`): handlers stay plain POST + 303. For a POST with `HX-Request`, the middleware replays the 303 as an internal GET and returns that page with `HX-Trigger` (`dash:flash` with key, the message the replayed page rendered, error flag, undo path), `Vary: HX-Request`, `Cache-Control: no-store` and `Dash-Revisions`. The writing tab skips SSE events at or below those revisions, so it does not refresh twice. A lapsed session answers `HX-Redirect` to login instead of morphing the login page into the list. `HX-Request` selects the response format only; it is never proof of origin. Trash calls `httputil.OfferUndo(w, restorePath)`: the undo is a single bodyless POST to that path (checked by `IsLocalPath`), so anything it restores must be encoded in the path or query. Plain posts (pages without a live container, like the idea page) instead redirect with `?undo=<restore path>`, which the layout shows as an undo button (`httputil.UndoFromQuery` accepts only local `/restore` paths). Purge, user deletion, move and bulk trash keep a confirm.

**Id scheme** (morph pairs elements by id): tracker rows and house projects `item-{slug}`, ideas `idea-{slug}`, maintenance `maint-{slug}`, plan rows `plan-{list}-{slug}` (`todos`, `family`, `house`). Suffixes `-toggle`, `-detail`, `-up`, `-down`, `-done`, `-drop`, `-substep-{n}-{toggle|promote|remove}`. Focus after change uses `data-row`, `data-row-focus`, `data-row-list` and `data-row-heading`. Renaming an item changes its slug and id, so it loses expanded state until Plan 3's stable IDs.

**Styles and themes:** three styles (`cards` default, `paper`, `document`) times two themes (light, dark) = six token blocks in `web/static/theme.css`, which is one file in `@layer reset, tokens, base, components, pages, utilities`. The default style's tokens sit in the plain theme blocks; others override in `[data-style="x"][data-theme="y"]` blocks. `data-style` and `data-theme` are set on `<html>` before first paint by the `appearance-script` partial (`_components/appearance.html`, also used by login) from `localStorage`. `internal/theme` parses the blocks from the embedded CSS (`theme.Styles`, `theme.Blocks()`; a style's block falls back to the default style's block). `--accent` is fixed per style and theme; the seasonal hue is decoration-only `--seasonal` from `seasonal.ColourFor(now, tokens)`, injected by the layout as one colour per theme. Non-colour tokens sit in a bare `:root` block and per-style structure blocks (`[data-style="paper"]`). At start-up `templates.go` checks that `ColourFor` finds a passing seasonal colour for every day of 2028. Contrast of every other token is checked only by `test/contrast_test.go`, not at boot.

**List pages:** todos, family and goals put open rows in `.tracker-list` beside a filter rail (counts from `filterCount`); ideas group rows in `<section data-row-list>` blocks per status.

**Two flat-file parser families:** tracker (`personal.md`, `family.md`, `house-projects.md`) trims every body line and drops blank lines; maintenance (`maintenance.md`) drops blank lines; ideas (`ideas.md`) preserve them. House uses two files because two services cannot safely read-modify-write one file. House projects are a `*tracker.Service` with `Budget`, `Actual`, `Status`.

**Soft delete:** `[deleted: YYYY-MM-DD]` instead of removal. The cache holds all items; `List()` and `Search()` filter deleted ones; `Get(slug)` does not (restore and purge need it). An hourly loop (first run an hour after start-up) purges items trashed 7 or more days ago, in the shared lists and in every user's lists via `auth.AllUsers`.

**Daily planner** (`internal/home`): `[planned: YYYY-MM-DD]` marks a task for a day; the planner is a view over tracker items, not a store. Overdue items are merged into each list's planned items and labelled "from <day>". `[plan-order: N]` persists manual order; `SetPlanned`/`ClearPlanned`/`BulkSetPlanned` reset it to 0. `sortPlanItems` puts ordered items first, then by priority. Drag-and-drop (`planner.js`) is delegated from `document`; reorder buttons and "drop" live in the expanded row and work on every pointer. `planner.js` sends `X-Requested-With`; `SetPlanned` and `ReorderPlanned` return 204 for it (`ReorderPlanned` also for `HX-Request`); the other plan handlers redirect.

**Timezone:** `config.Location` (`DASHBOARD_TIMEZONE`) is injected through constructors and `Deps`; template funcs needing local time are built by `buildFuncMap(loc)`. `auth` uses UTC deliberately. `insights` and `seasonal` are pure functions taking `time.Time`.

**MCP sidecar** (`mcp/`): Python FastMCP over Streamable HTTP, 24 tools (5 read-only, 15 write, 4 destructive registered only with `MCP_ALLOW_DESTRUCTIVE=true`). Inbound `MCP_TOKEN` and outbound `DASHBOARD_API_TOKEN` must both be 32+ characters and differ. `mcp` is pinned `<2` (2.x renamed `FastMCP`).
</ARCHITECTURE>

<CONVENTIONS>
- Inline metadata (`!high`/`!medium`/`!low`, `[added:]`, `[completed:]`, `[goal:]`, `[status:]`, `[tags:]`, `[deadline:]` (goals only), `[planned:]`, `[plan-order:]`, `[from-idea:]`, `[converted-to:]`, `[deleted:]`, `[budget:]`, `[actual:]`, `[cadence:]`, `[images:]`, and `[project:]` on ideas) is parsed from unindented checkbox lines only. Titles containing bracket patterns are a known limitation. A new tag touches: the parser, `writeItem`'s output order (and so the round-trip fixtures), `itemToAPI` in `tracker/api.go`, and `inlineMetaRe` in `httputil/validate.go`, which the tracker API (not the ideas API) uses to strip tags from titles and bodies; miss that and API or MCP input can inject the tag. House projects share the tracker parser.
- Title edits re-slugify; the old slug is invalid after the mutation.
- `auth.TemplateData(r)` returns the base map (`UserName`, `IsAdmin`, `CurrentPath`); handlers merge page data into it. Read `UserName` with a comma-ok assertion.
- Flash messages: `?msg=key`, resolved per package (`resolveFlash` in tracker and ideas with `httputil.RotatingFlash` variants; house has no variants; home uses `resolvePlanFlash`). Only `flashErrorKeys` render as errors (`role="alert"`); note `bulk-deleted` is one. `HX-Trigger` carries the key and rendered text, never item titles.
- 500s use `httputil.ServerError` (correlation id). 400s use `http.Error` with a specific message. Redirect targets go through `httputil.IsLocalPath`.
- Markdown renders through goldmark + bluemonday UGC and is cast to `template.HTML` in handlers. In the func map only `linkify` may return `template.HTML` (`TestFuncMapHTMLFunctionsLimited` parses `templates.go`).
- Image captions are stored inline as `filename|caption` in `[images:]`. Captions travel in separate `caption-N` form fields (not the comma-separated `images` input) and `httputil.ReconstructImages(r)` zips them back. `SanitiseCaption` strips `|,]<>"` and truncates to 200 runes; `splitImageCaption` returns plain strings, never `template.HTML`. Uploads are shared, with random hex filenames and no ownership tracking.
- Templates reference static files as `{{static "name"}}` (hashed `?v=` URL, `immutable` only when the hash matches). A test forbids hard-coded `/static/` URLs.
- Module and component templates must not use inline `on*` handlers; use the delegated `data-action`, `data-confirm`, `data-submit`, `data-autosubmit`, `data-stop-click` attributes handled in `tracker.js`. Core templates still have a few inline handlers (CSP `script-src` tightening is a follow-up).
- CSS: use tokens (colour, `--sp-1`..`--sp-7`, `--text-xs`..`--text-2xl`, radius, `--dur*`, `--w-*` widths), the `.btn` base with variants, and the right `@layer`. Coarse-pointer 44px minimums live in `utilities` because under `@layer` a `base` rule loses to any component `min-height`. No `opacity` below 1 to dim text (it breaks contrast; use `--text-muted`). New colours are tokens in the two default blocks at least (other styles fall back to them, as `--attention` does); override per style only where needed. A new text colour must be added to `textTokens` (and a fill to the soft-pair map) in `TestThemeTextTokensContrast`, or only the rule audit checks it. All animation respects `prefers-reduced-motion`.
- JS is ES5 (no `const`/`let`/arrow functions) and binds interactive listeners on `document`, never on elements inside a `[data-live]` container.
- Dialogs are native `<dialog>` with `showModal()`. Confirms go through `confirmAction` (`dialog.js`): forms use `data-confirm`; bulk delete uses `data-submit="bulk-delete"` → `confirmBulkDelete`; admin user delete calls it inline.
- Bulk actions use `mutateBatch` so one file write covers every selected item.
- Edits: `tracker.Service.UpdateEdit` replaces body, tags and images, so only callers that hold every field (the web edit form) may use it. Callers that may not (the API, the house page, which has no image controls) use `ApplyEdit`, where nil fields keep their values.
- Date cutoffs use `httputil.CutoffDate(days, loc)`; pass the injected location.
</CONVENTIONS>

<GOTCHAS>
**Indented lines are body content.** Only unindented checkbox lines start an item and only unindented `#` lines end one, in all three parsers. Indented checkboxes are sub-steps in tracker, log entries (`- [x] YYYY-MM-DD - note`) or notes in maintenance, and body text in ideas, except that an indented checkbox before any idea starts one. Ideas and maintenance treat a tab as one indent level; tracker trims body lines. `writeItem` indents bodies with 2 spaces, so checking `trimmed` instead of `line` creates spurious items on re-parse. Round-trip fixtures in `test/testdata/roundtrip/` must stay byte-identical; the `*_normalise.md` fixtures instead match their `.golden` files (documented normalisations).

**"personal" vs "Personal":** `"personal"` is the category and `ToTask` target; `"Personal"` is the markdown heading in `config.go`. Module ID is `todos`. Don't conflate them.

**`MoveToList` adds to the target, then calls `PermanentDelete` on the source.** `Delete` would leave a ghost in Recently Deleted; deleting first could lose the item on a failed add.

**Never hold two service locks at once.** `toTask` (in `internal/modules/ideas`) writes ideas and a tracker service; search queries `Searcher`s one at a time in registration order.

**Morph pairs id-less elements by tag.** Give `data-morph-skip` elements and stateful elements (`<details>`, expandable rows) unique ids, or idiomorph pairs them with an unrelated new element and drops content or state (`TestMorphSkipElementsHaveIDs` covers skip elements only). Do not reintroduce refresh-suppression flags (`TestNoRefreshSuppressionFlags`); declare kept state with `data-keep-*` or hold the refresh.

**Commentary loads by XHR on expand** (`tracker.js` `loadCommentary`). Do not use `hx-trigger="revealed"` inside live containers: it fires during node processing and requests every item at once. The endpoint returns 200 with an empty body when there is nothing. Ironclaw writes commentary via the API but is not deployed.

**Maintenance log order:** entries `- [x] YYYY-MM-DD - note` are written newest first and `NextDue` uses `Log[0]`. A hand-edited file with oldest first computes from the wrong date.

**House `UpdateStatus("done")`** sets `Done` and `Completed` so digest counts it; moving away from done clears both.

**Ideas-to-task:** `toTask(ctx, title, body, tags, fromIdeaSlug, target)` takes target `personal`, `family` or `house` (house projects start with `Status = "todo"`) and returns the new slug. Conversion marks the idea `converted` with `[converted-to:]` and the task gets `[from-idea:]`. Permanent delete of either side leaves a dangling reference (accepted).

**Sub-step indices** address steps by position; two tabs editing one task's steps can act on the wrong step (accepted).

**Watcher matches exact filenames** from `WatchSpec`s (shared `Path` or `USER_DATA_DIR/{id}/{UserFile}`). Atomic-write temp files (`.<name>.atomic-*.tmp`) never match; `config.Load` removes stale ones at start-up. Events go to every SSE client (no per-user routing).

**MCP `stateless_http=True` runs the lifespan per request:** keep the `httpx.AsyncClient` a module-level singleton in `client.py`. `StreamableHTTPSessionManager.run()` runs once per instance, so tests share a module-scoped `TestClient`; requests need `Accept: application/json, text/event-stream`.
</GOTCHAS>

<TESTING>
`make lint test` locally (`test` is `go test -count=1 -race ./...`); set `INTEGRATION=1` for the concurrent-reader test, as CI does. Go tests live in `test/` as map-based table tests; temp dirs and in-memory SQLite, no external services. `make vuln` needs network access the sandbox may block.

Guard tests worth knowing: route goldens (`test/testdata/routes_*.golden`, both auth modes identical; explain any diff in the plan), `TestModuleContract`, contrast tests in `test/contrast_test.go` (`TestThemeRuleTextContrast` checks every `color:` rule in all six blocks, `TestThemeNonTextTokensContrast` holds focus ring and edges at 3:1), and `TestE2ESelectorsExist`, which fails when a Playwright spec selects a class or id no template or app JS defines. Run it after renaming any class or id.

Playwright (`e2e/`, axe in all three styles and both themes) cannot run inside the nono sandbox; outside it `bash e2e/run.sh [spec | --grep pattern]`. In CI, screenshots are a separate non-gating job, and `e2e-grep.yml` re-runs a `--grep` subset on a pushed ref.

MCP: `cd mcp && pip install -r requirements-dev.txt && pytest test_smoke.py -v` (sets its own test tokens; respx mocks the dashboard API).
</TESTING>
